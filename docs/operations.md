# 運用ドキュメント

triptych の collector が外部ソースへどうアクセスするか、同期・検知がどう動くか、トラブル時に何を見ればよいかをまとめます。設計の背景は [`specs/mvp-core/design.md`](../specs/mvp-core/design.md) を参照してください。

## 外部ソース一覧と収集マナー

collector は `backend/adapters/` 配下のソースごとに独立したアダプターを持ち、各自がレート制御・キャッシュ・User-Agent明示を担当します。ユーザーデータは一切保持せず、外部レスポンスのキャッシュのみをSQLite（`backend/cache.db`）に持ちます。

| ソース | 用途 | レート制限 | キャッシュTTL | 備考 |
|---|---|---|---|---|
| AniList (`anilist.py`) | アニメの放送予定・relations（原作→アニメ・続編）・原作エントリの解決・検知 | 25 req/min（実際の上限は 30/min。バースト4） | 検索1h / 詳細6h | GraphQL API。成人向け（isAdult）は除外。放送日は JST・朝5時区切り（`25:30` 表記） |
| なろう小説API (`narou.py`) | Web小説の検索・話数・更新日・完結 | 1 req/s | 検索1h / 詳細6h | 公式API。検索は `title=1&type=re&order=hyoka`（タイトルのみ・連載のみ・評価順）。`end` は 0=完結/短編、1=連載中。R18 API は使わない |
| openBD (`openbd.py`) | ISBN引きの書籍情報・発売日（まとめ取り可） | 2 req/s | 詳細6h | ISBN検索専用。大手版元は pubdate が空のことが多いので NDL の日付で補う |
| NDL Search (`ndl.py`) | 紙の新刊・近刊の探索、書籍のシリーズ検索 | 1 req/s | 6h | 国会図書館サーチ OpenSearch API。`mediatype=books&from=<2年前>&cnt=500` を全件取得してから発行日順に並べる。近刊（出版予定）も入る。発行日は初版日に近く、書店の発売日と数日ずれることがある |
| しょぼいカレンダー (`syoboi.py`) | 放送局・配信サービスの番組と配信開始 | **60秒に1回**（robots.txt の `Crawl-delay: 60`） | 結果24h / チャンネル表7日 / 見つからない6h | 専用キューで取得し、未取得の間は `queued` を返して次の同期で拾う。初回は3リクエストで約2分。番組は14日前から取る（配信中のサービスの判定用で、リクエストは1回のまま。DTO の `programs` は今日以降だけ） |
| カクヨム (`kakuyomu.py`) | 作品の検索・話数・最終更新・完結（API非提供のためスクレイピング） | 1 req/s + 同時実行1（`asyncio.Lock`） | 検索1h / 作品24h | robots.txt をパスごとに確認。生HTMLは返さず正規化DTOのみ返す。日付は UTC から JST に変換 |

見送ったソース: 版元ドットコム（書誌の利用可否が不明）、楽天ブックス API（鍵が必要）、Google Books（鍵なしは日次枠0）、ハーメルン・ノベルアップ+（ボット拒否）、pixiv ノベル（規約でクローラー収集を禁止）。詳細は `specs/data-coverage/design.md`。

共通ルール:

- **User-Agent**: 全リクエストで `triptych/0.1 (personal tracker)` を明示します。
- **robots.txt**: スクレイピング系（カクヨム）は `robots.txt` を取得・パースし、パスごと（`/search` と `/works/`）に `can_fetch` を確認します。偽なら `SourceUnavailable`。取得に失敗した時は締め出さず、次の呼び出しで取り直します。
- **health**: 各ルーターは `SourceUnavailable` を捕まえると `backend/errors.py` の `record_adapter_error` で記録し、`/api/health` がソースごとの直近エラーを返します（回復後も時刻つきで残ります）。
- **レート制御の実装**: `backend/ratelimit.py` の `TokenBucket`（`rate`/`capacity` トークンバケット）を各アダプターが1インスタンスずつ保持します。API系は `acquire()` でブロッキング待機、スクレイピング系はさらに `asyncio.Lock` で同時実行数を1に絞ります。
- **キャッシュの実装**: `backend/cache.py` の `TTLCache`（SQLite backed）。`get()` は期限切れエントリを遅延削除し、ミス扱いにします。手動プル時のみ `?refresh=1` で強制更新できます（キャッシュを無視して再取得）。
- **紙の新刊の分業**: 探索は NDL Search が主役です（`GET /api/ndl/series?title=&kind=novel|manga&line=`）。翻訳（978-4 以外の ISBN）・電子書籍・アンソロジー・特装版などを除き、NDC 分類で小説（913.x）と漫画（726.x）を分け、叢書名で本編とジュニア文庫などの系統（line）を分けます。日付の精度が月・年しかない近い巻だけ、openBD をまとめ取り1回で照会して日付を補います。巻の同一性は ISBN で判定します。

## 同期の仕組み

実装: `src/lib/sync/engine.ts`

- **トリガー**: アプリ起動時、および Home の「今すぐ同期」（手動）。手動同期は1hスロットルを無視し、しょぼかる以外の全エンドポイントに `refresh=1` を付けてキャッシュを取り直します。しょぼかるは `Crawl-delay: 60` のため、手動でも24時間キャッシュを使います。
- **1hスロットル**: 前回同期から1時間未満なら、起動時の自動同期はスキップします。
- **対象は追跡中Editionのみ**: `status ∈ {plan, active, paused}` の Edition だけが対象です。
- **メディア種別ごとの振り分け**:
  - **アニメ**: AniList の `media` でシーズン開始・次話・放送状態、しょぼかるで配信サービスごとの配信（`stream-start`）を取ります。次話は1件だけのローリングで、放送が終わると消えます。毎週出るので新着にはせず、直近とカレンダーにだけ出します。しょぼかるが `queued` を返した時は黙ってスキップし、次の同期で拾います
    - **しょぼかるは AniList のあと**に照会します（同じ同期で取れた放送状態を使うため。NDL・なろう・カクヨムは並行）。Edition の AniList id がすべて放送終了（FINISHED）・中止（CANCELLED）なら照会しません（Crawl-delay 60 の枠を使わない）。放送中・放送前・休止中の id が1つでもある時と、AniList が取れず状態が分からない時は照会します
    - **配信を始めるサービス**: まだ配信の無いサービスは、そのサービスの最初の番組を配信開始（`stream-start`）の Release にして、新着にします。放送中の期に後から始まる別のサービスも同じです
    - **配信中のサービス**: 直近14日に配信のあったサービス（collector の `startedStreams`）は、配信開始ではなく「配信中」として、次回の配信を1件のローリング（`Release.rolling = true`・既読）で持ちます。日付は同期のたびに動かし、延期（`dateHistory`）にはしません。同じサービスの別チャンネルに替わっても（ABEMA は週ごとに替わることがある）1件のまま追います。新着・直近7日・カレンダーには出さず、Work 詳細の「次話と配信先」（行は「配信中」と表示）と、次話の行の「◯◯ 配信中」で表します。以前の同期が配信開始として作った行は、配信中になった時に既読のローリング1件へ作り直します。`startedStreams` を返さない古い collector では、放送中（RELEASING）の期の配信をすべて配信中とみなします
    - **既知の限界**: 直近14日に配信が無いサービスは、まだローリングの行を持っていなければ配信開始として扱います（2週以上休んだ後に初めて同期した時、休止中に登録した時など）。すでにローリングの行を持つサービスは、休みが2週以上続いても配信中のまま追います
  - **文庫・漫画**: sourceRefs に関係なく、Work のタイトルで NDL の新刊を引きます（文庫は小説、漫画はコミックの分類）。採用した系統（本編・ジュニア文庫など）は `syncHints.ndlLine` に保存して次回も使います。巻は ISBN で照合します。AniList の sourceRef は検知用の ID としてだけ使い、Release は作りません
    - **目録前の近刊**: collector はカタログ（`backend/catalog.db`）に JPRO 収集器が入れた近刊のうち、題名が Work タイトルで始まる巻を足して返します（検索結果に無い ISBN だけ。同じ ISBN は1冊のまま）。NDC の無い近刊の種類（小説・漫画）はカタログの判定を優先します。カタログが無い・古い時はこれまでどおり検索結果だけです。カタログの近刊を新しくするには `build --recent`（下の「カタログ」）
    - **叢書名のゆれ**: 近刊は叢書名を NDL の目録と違う書き方で持つことが多い（「モーニング KC」/「モーニングKC」、「ヤンマガKCスペシャル」/「ヤンマガKC」）。同じ出版社・同じ種類の目録済みの系統の書き換えか、どちらかがもう一方を含む名前なら、その系統の巻として返します。`ndlLine` が近刊の書き方で保存されていても巻を拾います。まったく別の名前（「Letter Comics」/「No.9 COMICS」）は別の系統のままです
  - **Web小説**: なろう・カクヨムから話数・最終更新・完結を取ります。`progress.total` だけを更新し、既読位置（current）と単位は変えません。最新話は1件のローリングで、話数が増えた時だけ新着にします
- **日付と精度**: アニメは JST・朝5時区切り（深夜1:30は前日の `25:30`）。年だけ・年月だけの日付は精度つきで持ち、「2026年8月」のように表示します。
- **延期の記録**: 日付が変わった時、新しい日付が旧日付の精度の範囲外に出た場合だけ `dateHistory` に記録します（「2026年8月」→「8/25」は精緻化なので記録しない）。
- **新着の扱い**: 新しく見つけた Release のうち、日付が過去のもの（登録直後に取り込んだ既刊など）は最初から既読にします。手動で足した Release は同期で上書きも削除もしません。
- **失敗時の扱い**: ソース単位でスキップして続行します。どのソースも成功せず失敗がある時は最終同期時刻を進めないので、次の起動で再試行されます。エラーは Home の同期状態と Settings の「同期」に出ます（検知のエラーは「検知」として表示）。

## 検知の仕組み（アニメ化検知）

実装: `src/lib/sync/detect.ts`

- **対象**: 追跡中の Edition を持つ Work（原作系と、続編を探すためのアニメ）。
- **3つの経路**（信頼度の高い順）:
  1. **続編（sequel）**: 追跡中のアニメの AniList id から relations の SEQUEL を最大3段辿ります。放送済みの期は通り抜けて、その先の新期を探します
  2. **原作から（relation）**: 原作の AniList NOVEL/MANGA id から relations の ADAPTATION（アニメ）を辿ります。id は sourceRefs の anilist → `syncHints.anilistSourceId` → `resolve-source`（タイトルから原作エントリを解決）の順で決め、解決した id は保存します。次の2つを足して辿ります
     - **原作の続きの部**: 部ごとに別エントリの原作（本好きの下剋上の第二部〜など）は、原作から SEQUEL を最大3段辿り、その ADAPTATION も見ます。辿るのは、NOVEL/MANGA の別が同じで、副題を除いた題名が同じ（一方が他方で始まる）ものだけです。外伝や別作品の続編は辿りません
     - **新しい期の続編**: 原作から見つけたアニメのうち新しい2期（開始日の無いものは発表直後とみて先頭）から、SEQUEL を同じシリーズの題名に限って辿ります。新期が前の期の続編としてだけ登録され、原作の ADAPTATION に無いことがあるためです（かぐや様の完結編など）。この経路で見つけたものは `via=sequel` で記録します
     - **照会の上限**: 上の2つで増える relations の照会は Work ごとに最大6回です（この実行で照会済みの id は数えません）
  3. **タイトル一致（title）**: 上の2つで id が決まらない Work だけ、従来の `title.native` 照合（閾値 0.85）を使います
- **提案しないもの**: 放送済み・中止の期（検知は「発表を知る」ため）、どの Work でも既に登録済みのアニメ、同じ組の検知が既にあるもの（却下・承認済みを含む）、MUSIC 形式、成人向け。
- **24h/Workスロットル**: Work ごとに24時間に1回。その Work の照会が全部成功した時だけ記録するので、失敗した Work は次の同期で再試行されます。
- **既知の限界**: 題名が変わる続編は、原作から辿る経路（2）では拾えません（化物語→偽物語など）。続きの部も新しい期の続編も「副題を除いた題名が同じ」ことを条件にするためです。そのアニメを追跡中の Edition として登録すれば、続編の経路（1）は題名を問わず SEQUEL を辿るので拾えます。
- **accept時の挙動**: 承認するとアニメ Edition が作られ、放送開始日があれば精度つきの Release として追加されます。

## カタログ（大量収集データ）

あなたの追跡データ（端末の IndexedDB）とは別に、collector 側の `backend/catalog.db`（SQLite・git 対象外）に作品カタログを持ちます。実装: `backend/catalog/`、仕様: `specs/catalog/`。

- **作る**: `.venv/bin/python -m backend.catalog build`（全ソース→紐付けまで。初回は AniList が約1時間半、他は並行して1時間前後、JPRO の近刊が 12〜22 分）。取り終えた区切りは飛ばすので、途中で止めても同じコマンドで続きから再開します
- **ふだんの更新**: `build --recent`（全ソース→紐付けで約15分。JPRO 以外で約8分＋JPRO の近刊 4〜8 分）。新しい本・放送中の作品・上位の Web 小説・前回からの近刊だけを取り直し、既存の行は更新するだけで消しません。`scripts/launchd.sh install` 済みなら毎週月曜 5:30 に自動で走ります（設定画面と同じジョブ API。呼び出しの記録は `~/Library/Logs/triptych/weekly.log`）。新刊が気になる時は設定画面かここから手動でも。`--fresh` とは同時に使えません
- **設定画面から実行**: ふだんの更新（`build --recent`）は設定画面からも実行できます（API は `POST /api/catalog/jobs/recent`、状態は `GET /api/catalog/jobs/current`）。collector が子プロセスとして起動し、出力は `local/catalog-build-recent-<YYYYMMDD-HHMMSS>.log` に残ります（画面には末尾40行）。同時に走るのは1つだけで、実行中の再要求は 409 です。`local/catalog-job.lock` の排他ロックを子プロセスが握るので、collector を再起動しても子は止まらず（画面の状態は消えますが）、終わるまで別の更新は始まりません。ロックはプロセスが終われば OS が外すため、古いロックが残って詰まることはありません。ターミナルで直接走らせる `build`・`link` も同じロックを取り、設定画面の更新（または別のターミナルの `build`）が動いている間は `already running ...（pid n）` と出して何もせず終わります（終了コード 2）。`stats`・`export` は読むだけなのでロックを取りません
- **全部取り直す**: `build --fresh`（約2時間半）。`--recent` が見ない範囲（古い連載の状態、なろう・カクヨムの下位、昔の月の本、直近 30 日の近刊）まで新しくします。月1回程度
- **一部だけ**: `build --source anilist,ndl --no-link` のあと `link`（`--recent` とも組み合わせられます）。試運転は `--limit 200`

  `--recent` の範囲と目安（2026-10-15、前日に全件を取った DB で実測。合計 7分44秒 ＋ 紐付け 15秒）:

  | ソース | 取り直す範囲 | 件数 | 時間 |
  |---|---|---|---|
  | AniList | 今年から3年先までの年（と、それより先の作品）。放送中・放送予定（RELEASING / NOT_YET_RELEASED）のアニメ全部、予定のマンガ、連載中マンガの人気上位1000。最後に、保存済みで「放送中・予定」のまま今回見えなかった行（終了・中止・休止に変わった作品）を ID 指定で最大500件（アニメ優先、次に人気順） | 約4,900 | 約5分半（約110リクエスト） |
  | しょぼかる | 前回の実行の1日前以降に更新された番組だけ（`LastUpdate`）。前回の記録が無い・試運転だった時は全番組 | 約30〜数百 | 数秒（1リクエスト。collector が直前に取っていれば最大60秒待つ） |
  | なろう | 21ジャンル × 総合評価の上位1000 | 約20,500 | 約40秒 |
  | カクヨム | 12ジャンル × 人気順の上位100（5ページ） | 1,200 | 約1分 |
  | NDL | 先月・今月・6か月先までの月と、その先をまとめた区切り（小説・漫画）。月が500件を超えたら ISBN で割るのは全件と同じ | 約2,100 | 40秒〜数分 |
  | JPRO（目録前の近刊） | 前回最後まで終わった実行の1日前から今日までに更新された登録（日ごと）。記録が無い時は直近30日 | 週1回で約800（約8,000件中） | 4〜8分（約50リクエスト。1回1〜9秒） |

  `--recent` は全件の再開位置（途中で止めた区切り）に触れません。止めた時は同じコマンドをもう一度実行します（最初からやり直し）。画面の「最終収集」は `--recent` でも進みます
- **検索索引を変えたら**: 検索索引（`entries_fts`）の作り方を変えた時（検索用テキストの中身を変えた時など）は、`.venv/bin/python -m backend.catalog link`（約15秒）を実行します。`link` は紐付け・作品・索引を作り直すだけで、収集はしません（近刊の行のシリーズ名・巻だけは元の題名から分け直して書き戻します）。何度実行しても同じ結果になります（冪等）。実行するまでは古い索引のまま検索されます
  - 全角半角・大小文字の揺れは、検索用テキスト（`entries_fts.text`）に題名・別名・読みと、NFKC・小文字化で畳んだ形を入れ、検索語も同じに畳んで吸収します（半角の `spy×family` で全角の `ＳＰＹ×ＦＡＭＩＬＹ` が、全角カナで半角カナの題名が引ける）
  - 3文字以上はこの索引（trigram）、1〜2文字は索引が使えないので検索用テキストを1回だけ走査します（「薬屋」で約166ms→約56ms、2026-10-15 実測）
- **書き出し**: `python -m backend.catalog export`（`local/catalog/catalog-YYYYMMDD.csv` と `.json`）。画面の CATALOG タブからもダウンロードできます。CSV は Excel で文字化けしないよう BOM 付きで、`=` などで始まる題名は数式にならないよう `'` を付けます
- **件数を見る**: `python -m backend.catalog stats`
- **収集マナー**: AniList 20 req/min（応答の残数を見て待つ）、なろう・カクヨム・NDL 1 req/s、しょぼかるは collector と同じ記録を見て 60 秒に1回（1回の取得で足りる）
- **目録前の近刊（JPRO）**: `build --source jpro`。国会図書館サーチの OAI-PMH（`set=jpro`）から、出版社が出版情報登録センターに登録した近刊を、レコードの更新日（日本時間の日）ごとに取ります。発売日が先月1日以降の小説・漫画だけを残し、目録済みの本と同じ `ndl:<ISBN>` の行に入れます（`extra.via = "jpro"`）。目録済みの行の題名・叢書名は変えず、JPRO の発売日が細かい時だけ日付を更新します。目録ができると NDL の収集器が同じ行を上書きし、細かい日付は残ります
  - **範囲**: `build` は直近30日（`WINDOW_DAYS`。今の時点で約23,000件・約150リクエスト・12〜22分、残るのは約1割）。今日と昨日は CloudFront のキャッシュ（約23時間）があるので確定させず、次の実行で取り直します。`--recent` は前回最後まで終わった実行の1日前から。間が30日以上空いたら `--recent` を使います（`build` は直近30日しか見ない）
  - **飛ばす日**: 1日の件数を最初の1ページで見て、2万件を超える日は取りません（2026-09-27 に全件 約356万件の更新日が付け直された。`harvest_state` に `bulk: ...` と残ります）。その日にしか更新の無い近刊は、登録が次に更新されるか目録ができるまで入りません
  - **判定**: JPRO のジャンル語（「コミックス・劇画」「日本文学小説・物語」など）と NDC のリンクで小説・漫画に分け、ムック・絵本・写真集・実用書・資格書・成人向け・電子書籍を除きます。表は `backend/catalog/harvest/jpro.py` の docstring とテスト。2026-10-15 の試運転で残った500冊のうち明らかな誤りは7冊（写真集・戦術書・ビジュアルブックなど。規則を足して除外済み）
  - **書影**: 入れません。NDL のサムネイル（`https://ndlsearch.ndl.go.jp/thumbnail/<ISBN>.jpg`）は NDL Search 以外の Referer だと 403 になります
  - **シリーズ名と紐付け**: 近刊は巻を題名に書くので（「シャングリラ・フロンティア(28)エキスパンションパス ~…~」）、題名をシリーズ名・巻・版の語に分けます（`backend/catalog/text.py` の `split_volume_title`）。目録済みの巻がある本はその巻と同じ作品に、無い本は、注記を外した題名・巻の後ろを落としたシリーズ名・副題の前までの頭が作者の重なる AniList の小説/漫画・目録済みの本・なろう/カクヨムの作品に入ります。作者が無い・違う時は結びません。詳細は `specs/catalog/design.md` の「JPRO の近刊の紐付け」
  - **分け方を直した時**: `link` だけで反映されます（`.venv/bin/python -m backend.catalog link`、約15秒）。`link` が保存済みの元の題名（`extra.jpro.title`）から分け直し、違う行の `extra.series` / `extra.volume` を書き戻します（2026-10-15 は 478 行）。収集し直す必要はありません
  - **近日の表示**: 一覧の NEXT の横は本なら巻（「1巻」「28巻 エキスパンションパス」）。巻の無い本は題名で、作品の題名と同じなら出しません
  - **件数**: `stats` の「ndl rows from JPRO」の行に出ます（行そのものは `ndl` に数えられます）
- **取れないもの**: なろう・カクヨムは上位だけ（全件ではない）、目録前の近刊のうち NDL が一括で更新日を付け直した日にしか更新の無いもの、成人向け

## トラブルシュート

### collector が未起動のとき

- **フロントエンドの挙動**: 全ビューはIndexedDBのローカルデータのみで描画されるため、collectorが止まっていても閲覧・手動編集（ステータス変更・進捗入力・手動Work/Edition作成）は問題なく続行できます。
- **同期・検索・検知が失敗する**: 同期ボタン操作や検索操作を行うと、collectorへの接続に失敗した旨がエラーとして表示されます（Settings画面の「同期」セクション、または操作直後のエラーメッセージ）。
- **復旧方法**: 常駐させている場合は `scripts/launchd.sh status` で状態を、`scripts/launchd.sh logs` で理由を確かめ、`scripts/launchd.sh restart`（未登録なら `install`）。常駐させていない場合は `npm run api`（開発時）または本番相当の `uvicorn backend.app:app ...` を起動し直します。必要であれば手動プルで同期をやり直してください。
- **カレンダー**: カタログを読めない間、月の升目で選んだ日は「カタログの予定を出せません（collector に接続できません）」と出ます。

### 外部ソースが障害・レート制限中のとき

- Sync Engineはソース単位でスキップして処理を継続するため、他ソースの同期は影響を受けません。
- **見え方**: Settings画面の「同期」セクションに、最終同期時刻と、失敗したソースごとのエラーメッセージ・発生時刻が一覧表示されます（`src/routes/Settings.svelte` の `syncErrorEntries`）。エラーが無い場合は「エラーなし」と表示されます。
- 既存のキャッシュ済みデータ・ローカルデータでの表示は継続されるため、ユーザー操作をブロックすることはありません。

### スクレイピング先（カクヨム）のHTML構造が変わったとき

カクヨムアダプター（`backend/adapters/kakuyomu.py`）は、ページに埋め込まれたNext.jsのデータ島（`<script id="__NEXT_DATA__">` 内のJSON、Apolloキャッシュ形式）をパースして正規化しています。生HTMLの正規表現スキャンには依存していません。

構造変更が起きた場合の直し方:

1. **症状の切り分け**: `_extract_next_data()` がNoneを返す（`__NEXT_DATA__` タグ自体が無い）のか、`_parse_work_page()` 内で `state[f"Work:{query_work_id}"]` 等のキー参照が `KeyError` になる（JSON構造は健在だがフィールド名やネスト構造が変わった）のかを切り分けます。いずれの場合も `SourceUnavailable("kakuyomu", ...)` として扱われ、ユーザー影響は非侵襲的なエラー表示に留まります。
2. **fixtureの更新**: 実際のカクヨム作品ページのHTMLを取得し、`backend/adapters/`配下のfixture（録画済みレスポンス）を差し替えます。生HTML／scriptをそのままテストに含めても構いません（クライアントへは正規化DTOのみ返すため問題ありません）。
3. **アダプターの修正**: 新しいJSON構造に合わせて `_parse_work_page()` のキー参照（`work.get(...)` や `_resolve_ref()` によるApollo参照解決）を更新します。
4. **テストで確認**: `.venv/bin/pytest` を実行し、更新したfixtureに対する正規化テストが通ることを確認します。
5. **robots.txt / レートへの影響がないか確認**: 構造変更とは別に、対象パスの `robots.txt` 許可状況が変わっていないかも合わせて確認してください（`_ensure_robots_allowed()` が起動後最初のアクセス時に一度だけキャッシュする点に注意 — robots.txt側の変更を反映するにはプロセス再起動が必要です）。

同様の考え方は、将来 API非提供の別ソースをスクレイピングで追加する場合にも適用できます（正規化DTOへの変換・robots.txt確認・レート制御・fixtureテストの4点セット）。
